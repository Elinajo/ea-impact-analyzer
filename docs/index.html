The decision that matters

The model does not produce architecture facts

Structured relationships are queried. Prose is retrieved. The LLM does neither.

An architecture repository holds structured relationships. Asking which applications support a capability is a query, not a similarity search. The answer is computable, and therefore checkable.

Embedding that structure as prose and retrieving it throws the structure away, and replaces a correct answer with a plausible one for nothing in return. So retrieval is reserved for the part of the corpus that genuinely is prose — principles and decision records, where the question really is “what did we say about this” and there is no relation to traverse.

The substance

Owning data and reading data are not the same thing

OWNS means the application is the authoritative source for a data object. Retire it and that data is orphaned — nothing is authoritative for it any more.

CONSUMES means the application reads data it is not authoritative for. Retire it and the data object is untouched; only the consumer loses access.

A system that reports “retiring A05 affects D01, D02, D03, D05” is wrong. A05 consumes the first three and owns only the last. One generic USES edge would collapse the two cases together and report four impacted data objects where there is one.

Relationship types — the whole vocabulary
SUPPORTS
application → capability. The application realises part of the capability.
OWNS
application → data object. Authoritative source. Retiring it orphans the data.
CONSUMES
application → data object. Reads it without authority. Retiring it changes nothing for the data.
DEPENDS_ON
application → application. Retiring the target breaks the source.
RUNS_ON
application → technology. Orphaned only if this was the last application on it.

Technology is orphaned only if it was the last

A05 runs on T02 and T03, but A06 also runs on T02 — so only T03 is orphaned. A06 depends on A05, but A06 has not been retired, so it is still running.

Losing all support is stronger than being degraded

C04 is supported only by A05 and loses all support. C03 is supported by applications that merely depend on A05 — a weaker and separate claim, reported in its own list.

Epistemic boundary

What it refuses to answer

Asked “can we safely retire the Operational Data Platform?”, the system declines. It can enumerate architectural dependencies. It cannot determine operational safety, which needs service level requirements, a transition plan, migration arrangements for the data A05 owns, and an operational risk assessment. None of that is in the repository. Cost is not represented anywhere at all.

The refusal is not a keyword rule. The system prompt states what the repository contains and what it does not, and the refusal follows from that boundary — so it applies to any question the evidence cannot carry, not only to the two in the eval set. A keyword rule would score green on those two and prove nothing.

A confident yes or no scores zero, and it should. A system that expresses more confidence than its evidence supports produces over-reliance no matter how accurate it is elsewhere.

Where the keyword retrieval actually falls over

eval/retrieval_probe.py asks the same questions in words the documents do not use. Five of seven find the right document. The two misses are total:

ProbeExpectedResult
“What rule governs who is the master system for a dataset?” P01Not in top 3
“How should systems talk to each other?” P02Not in top 3
“Do we need a person to sign off on automated advice?” P03Rank 1
“Why is everything coupled to the operational data platform?” ADR-002Rank 1

These are vocabulary mismatches, not ranking errors. BM25 cannot connect “master system” to “authoritative source”, and no amount of tuning fixes that. It is precisely the case a vector index exists for. The hybrid retrieval is deliberately half-built — keyword first, so that what a vector index adds can be measured rather than assumed — and this probe is the measurement saying it would now be worth adding.

Written down as it went

DECISIONS.md holds one entry per architecture decision, written at the time rather than reconstructed at the end — including the ones where a proposal was changed, and why. Fifteen entries; nine still marked as proposals awaiting sign-off.

Deliberately not built

No web framework, no database, no ORM, and no vector index yet. The model is 22 elements: traversal over dictionaries is faster than a query planner would be, and the file stays readable and diffable in git.
